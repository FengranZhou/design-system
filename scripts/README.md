# 规范自动检测：怎么用

这套脚本把「设计规范」变成可执行的验收标准。本文只讲**怎么用**；
规则本身怎么定义、条目怎么来，见 `design-spec/references/judging-criteria.md`。

---

## 三种场景

### 场景一：在本仓库里改东西

什么都不用做——`pnpm build` 末尾会自动打印评分报告。

单独跑：

```bash
cd demo && pnpm audit:page     # 给 demo 打分
cd demo && pnpm audit:spec     # 查规范自身有没有裂缝（九类检查）
```

### 场景二：给下游项目验收 ⭐ 最主要的用法

**最省事**：demo 的「评判标准 → Checklist 检查清单」页右上角有**「复制评分指令」**按钮，
点一下复制，粘到那个项目的 Claude Code 窗口——CC 会自己跑脚本、读报告、按 hint 修，修完重跑确认。

**手动跑**：

```bash
node <设计系统路径>/scripts/audit-page.mjs ./src          # 扫目录
node <设计系统路径>/scripts/audit-page.mjs "src/**.vue"   # glob
node <设计系统路径>/scripts/audit-page.mjs ./src --json   # 供 CI 消费
node <设计系统路径>/scripts/audit-page.mjs ./src --quiet  # 只要结论
```

退出码 0 = 合规 / 1 = 不合规，可直接进 CI。

报告每条都指明**在哪一行、该怎么改、判据出自哪份规范**：

```
✗ [必须] el-button 的 type 仅允许 default/primary/danger
  el-button 的 type 仅允许 default / primary / danger
    src/views/CourseList.vue:42  <el-button type="warning">导出</el-button>

得分 87 / 100   ✗ 不合规
⛔ 2 条「必须」未通过 —— 只要有一条未通过即判不合规，与总分无关
📋 另有 21 条需人工确认（机器判不了，不计入上面的分数）
```

### 场景三：往仓库新增组件 / 设计模式

写规则时**在行末打标记**，条目就会自动进清单、自动出现在 demo 页面：

```markdown
- **新规则正文** <!-- @rule id=xxx level=MUST cat=组件用法 detect=regex dtitle=设计师看到的现象 -->
```

若标了 `detect=regex` 或 `ast`，**还要去 `detectors.mjs` 补一个同 id 的检测器**。

> **不用死记**：跑一次 `pnpm audit:spec`，漏打标记（C8）、缺检测器（C9）它都会报出来。

## 怎么读报告

**分数不是越高越好看。** 100 分只代表"没有静态可查的问题"——
报告末尾那批**需人工确认**的条目（弹窗标题写法、报错文案质量、分组合理性…）
机器判不了，而那些往往才是设计质量的关键。

修的顺序：

1. **先修全部「必须」项** —— 红线，一条不过即不合规
2. **「应该」项** —— 确有理由保留就写豁免声明（见下），否则修掉
3. **逐条核对「需人工确认」清单** —— 这步只能人来做

## 误报怎么办

**不要改检测器去迁就**——那会让规则越来越松。用豁免声明，并写清理由：

```vue
<!-- audit-ignore 这里确需 el-popover：要承载输入框+按钮，dropdown 放不了、dialog 过重 -->
<el-popover ...>
```

整个文件里某一类条目都要豁免（如演示页故意展示各种形态）：

```vue
<!-- audit-ignore-file badge-max-99 本页演示 Badge 各数值形态，故意不都加 :max -->
```

> **理由必须写清楚**——豁免是给规则开的口子，写明白才能在日后复核时判断它是否仍然成立。
>
> 若确认是检测器本身判错了（而非你的代码有特殊情况），告诉设计系统维护者具体是哪条，
> 改检测器比堆豁免更根本。

## 各脚本职责

| 脚本 | 干什么 | 什么时候跑 |
|---|---|---|
| `extract-rules.mjs` | 从规范正文的 `@rule` 标记提取条目 → `rules.generated.json` | 已挂进 `pnpm dev/build`，不必手动 |
| `audit-page.mjs` | 扫代码出违规报告 + 合规分 | 验收时；构建末尾自动跑（只警告） |
| `detectors.mjs` | 检测规则（正则 + AST），按 id 挂到条目 | 新增条目时来补 |
| `template-ast.mjs` | 轻量 Vue 模板解析器（不依赖 compiler-sfc） | 被 detectors 调用 |
| `audit-spec.mjs` | 规范自身的九类一致性检查 | 改完规范跑一次 |
| `audit-precision.mjs` | 多档位体系的取值精度检查 | 新增令牌档位后跑 |
| `component-catalog.mjs` | 组件目录：供「复制到 CC 使用」消费的组件清单 + 配置项 | 新增/改组件规则时同步 |
| `build-prompt.mjs` | 把「组件 + 配置 + 落点」拼成粘贴进下游 CC 的 prompt | 被扩展面板调用 |

> 后两个属于**「复制到 CC 使用」**功能（浏览器扩展里挑组件 → 页面上选落点 →
> 复制 prompt → 粘进下游项目 CC 窗口）。用法与维护纪律见 **`组件复制到CC.md`**。

**本地 vs CI 的构建差异**（`demo/package.json`）：

- `build` → `extract-rules`（**写盘**），本地用
- `build:ci` → `check-rules`（**只校验不写盘**），`vercel.json` 指向它

构建环境可能只读，且生成物已在版本库里、重新生成没有意义。
用 `--check` 还有个附带好处：**改了规范却忘提交生成物时，构建会失败并提示**，
比静默部署旧数据安全。

## 能力边界

**只覆盖「静态可查」的部分。** 当前 87 条条目里 66 条可自动检测、21 条须人工。

判不了的典型：

| 条目 | 为什么判不了 |
|---|---|
| 弹窗标题要写清操作对象 | 分不出「删除用户张三」和「确认操作」哪个具体 |
| 错误文案两段式 | 判断不了「手机号需为 11 位」比「格式不正确」好在哪 |
| 状态列必用 Tag | 得先知道哪一列是状态列 |
| 选项 >200 换 select-v2 | 选项数量运行时才知道 |

**跑到 100 分 ≠ 页面设计得好**——信息密度、视觉层级、文案是否得体，仍须人工审。

> 评分器仍在成熟中（已修过 template 截断、多处误报）。
> 第一次在真实项目上跑，大概率还会遇到新的误报——那时把具体条目反馈给维护者。
