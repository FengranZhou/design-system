# antd 3 适配层 —— 迁移方法论（从 Button 试点提炼）

> **本文回答一个问题：怎么把剩下 51 个组件迁得又快又准，不再重复 Button 踩过的坑。**
>
> 来源不是推演，是 Button 试点的实测——12 条差异、6 轮返工、2 次「自查通过后被用户点出 bug」。
> 具体差异清单见 `DIFF.md`，本文只讲**方法**。

---

## 一、先说结论：为什么做不到"一次性完美"

Button 一个组件挖出的 12 条差异，按「能否提前预知」分类：

| 类别 | 条数 | 能否靠读源码发现 |
|---|---|---|
| CSS 层差异（色值、圆角、阴影、字距） | 5 | ✅ 能 |
| **DOM 结构差异**（无 icon 插槽、loading 插节点） | 3 | ⚠️ 读 DOM 能发现，但要真的去读 |
| **JS 行为差异**（插空格、波纹、Wave 属性注入） | 3 | ❌ **完全不能**——必须跑起来 |
| **特异度战争**（antd 状态样式压过覆盖层） | 1 | ❌ 规则"存在"但不生效，静态查不出 |

**结论**：约 1/3 的差异只能在浏览器里发现。所以正确的目标不是"一次做完美"，
而是**"用一套固定流程，让每个组件一轮就收敛"**——把返工从 6 轮压到 1~2 轮。

## 二、单组件迁移标准流程（照此执行，别跳步）

### Step 0 —— 读 EP 源头，列出「能力清单」

打开 `el-theme/components/<组件>.scss`，把它**实现了什么能力**列成表：
类型 / 状态 / 配置项 / 约定 class / 特殊行为。这是验收基准，不是参考。

⚠️ **重点看顶部「接入方速查」注释**——它已经把该组件的全部对外能力写清楚了。

### Step 1 —— 读 antd 3 的 DOM 与 JS，先找"结构性断裂"

**这一步最容易跳过，也最贵。** 要查三件事：

```bash
# ① DOM 结构：类名、状态类、有没有对应的插槽/节点
grep -oE 'ant-<组件>-[a-z-]*' node_modules/antd/lib/<组件>/*.js | sort -u

# ② JS 行为：有没有改 DOM 内容 / 注入属性 / 插入节点
grep -nE 'insertSpace|cloneElement|createElement|setAttribute|Wave' node_modules/antd/lib/<组件>/*.js

# ③ 官方开关：能不能用 ConfigProvider 关掉某个行为
grep -rn 'configConsumerProps' node_modules/antd/lib/config-provider/index.js
```

**判据**：凡 antd 在 JS 里**改了 DOM 内容或插入节点**的，都是 CSS 压不掉的硬差异，
必须走 ConfigProvider 或调用方配合。Button 的两字中文插空格就是这么找到的。

### Step 2 —— 写覆盖层，遵守四条硬纪律

1. **每个状态显式对位，不要指望继承**
   antd 的状态样式特异度普遍高（`.ant-btn-primary:hover` 双类名），
   常态规则不会自然传导到 hover/active/focus。**三态各写一遍。**

2. **`:focus` 必须写成 `:focus:not(:hover):not(:active)` 且复位到常态**
   ⚠️ **这条是本次最大的坑**：focus 由点击触发**且持续存在**，
   若给它配 hover 外观，用户点完鼠标移开，外观**停在 hover 态不还原**。
   EP 的写法 `&:not(.is-text):focus:not(:hover)` 已经把这件事写对了，照抄口径。

3. **无底形态（text）要从所有实心规则里排除**
   给实心态的 hover/active/focus 全部加 `:not(.btn-text)`，
   否则实心规则特异度更高，会把文本按钮填成实心块。

4. **内部布局对齐 EP 的 flex 模型**
   antd 是 `inline-block` + `vertical-align`，而 `vertical-align:middle` 对齐的是
   **x-height 中线不是盒中心**，**中文下必然偏移**。改成 `inline-flex; align-items:center`。
   ⚠️ 但**不要顺手加 `line-height:1`**——行高必须由字阶令牌整档提供（见铁律）。

### Step 3 —— 浏览器实测（**不可跳过，这是唯一有效的验收**）

**静态查 CSS 规则"存不存在"是无效验收**——本次实测：7 条交互规则全部"✓ 存在"，
但实际渲染是错的（被 antd 更高特异度规则压掉）。

必须做这四项，用本目录 `scripts/` 下的探针脚本：

| 检查 | 方法 | 判据 |
|---|---|---|
| **色值/尺寸** | 读 `getComputedStyle` | 与令牌真值逐项比对 |
| **三态最终值** | 逐状态计算最终生效值 | 出现 antd 裸色（`rgb(64,169,255)` 等）即失败 |
| **点击还原** | 模拟 mousedown→mouseup→click→focus→mouseout | 外观必须回到点击前 |
| **垂直对齐** | 各子元素中心 vs 按钮中心 | 偏移须 < 0.6px |

⚠️ **自己写的检查器也会骗人**：本次我的 `:not()` 解析有 bug，误报 2 处。
**最终判据永远是浏览器的 `getComputedStyle`**，不是自己解析 CSS。

### Step 4 —— 人工点检（**机器替代不了**）

跑完 Step 3 全绿之后，**仍然要人去点**。本次两个 bug 正是这样发现的：
- 文本款 hover 变绿色胶囊
- 点击后颜色不还原

**必点清单**：每种形态 hover 一次、点击一次、点完把鼠标移开、Tab 键走一遍。

## 三、通用坑清单（写任何组件前先扫一遍）

### A. JS 行为类（CSS 无解，必须 ConfigProvider 或调用方配合）

| 坑 | 表现 | 解法 |
|---|---|---|
| 两字中文插空格 | 「确定」→「确 定」 | `<ConfigProvider autoInsertSpaceInButton={false}>` |
| 点击蓝波纹 | 扩散一圈 `#1890ff` | 压掉 `[ant-click-animating*]::after` 的 shadow/anim/display |
| loading 插入节点 | 按钮宽度跳变 | 需决策（接受 / 绝对定位 / 不显示） |

> **推论**：其它组件大概率也有各自的 JS 行为（Table 的排序图标、Select 的 tag 收起、
> DatePicker 的 moment）。**每个组件的 Step 1 都要重新查一遍，不能假设"Button 查过了"。**

### B. 特异度战争类

- antd 状态规则普遍是双类名（0,4,1），覆盖层单类名（0,3,1）会输
- **判据**：最终生效值里出现 antd 原生裸色 = 脱离设计系统 = 必须修
- **别用 `!important` 硬压**——会让后续维护无从下手；用等价或更高特异度的选择器

### C. 工具链类（一次性，配好就不用管）

| 坑 | 解法 |
|---|---|
| `global is not defined` 白屏 | index.html 里 `window.global = window.globalThis`（**`define` 无效**） |
| less 报错 | `css.preprocessorOptions.less.javascriptEnabled = true` |
| 改 lockfile 后白屏且无报错 | 重启 dev server（`--force`），ES module 加载失败 `onerror` 捕获不到 |

### D. 我自己犯的方法论错误（别重蹈）

1. **拿 HTTP 200 当"页面能跑"** —— Vite 的预处理器错误是浏览器端 overlay，HTTP 仍是 200
2. **拿"CSS 规则存在"当"规则生效"** —— 存在 ≠ 赢得特异度
3. **修 A 状态时顺手给 B 状态套同样的值** —— focus 套了 hover 的值，导致点击后不还原
4. **只抄表面不看机制** —— 照抄了 EP 的 `vertical-align:middle`，没注意 EP 内部其实靠 flex

## 四、怎么让 51 个组件跑得更快

### 4.1 按"结构相似度"分批，不要按字母序

| 批次 | 组件 | 特征 | 预估难度 |
|---|---|---|---|
| **第一批** | Tag / Badge / Divider / Alert / Empty | 纯展示、无状态机、无 JS 行为 | 低，可批量 |
| **第二批** | Input / Checkbox / Radio / Switch / Slider | 有状态机，但 DOM 简单 | 中 |
| **第三批** | Select / Dropdown / Tooltip / Popconfirm | **浮层类**，DOM 在 body 上、有 JS 定位 | 高 |
| **第四批** | Table / Form / DatePicker | **API 级差异**（列配置 / moment / Form.create） | 最高，可能需组件层封装 |

**先做第一批**能快速积累复用规则；**第四批要单独评估**，DatePicker 的 moment 依赖
不是样式问题，很可能需要在调用方封装转换层。

### 4.2 把探针脚本固化成工具

本次写的四个探针（色值比对 / 三态最终值 / 点击还原 / 垂直对齐）应该固化为
`antd3-theme/scripts/audit-component.mjs`，对每个组件跑同一套。

这与你现有的 `audit-page.mjs` 是同一思路——**把验收从"人的自觉"变成"可执行的脚本"**。

### 4.3 先建"公共基座"，避免 51 次重复

Button 里有一批规则是**所有组件都要的**，应抽成 `antd3-theme/base.less`：

- 关掉全局波纹（不只按钮，antd 的 Switch/Checkbox/Radio 都有）
- 压掉 antd 的 `box-shadow` / `text-shadow` 默认值
- 统一 focus 口径（`:focus:not(:hover)` 复位常态）
- ConfigProvider 的必配项（`autoInsertSpaceInButton={false}` 等）

**这一步做在前面，能省掉后面 51 次重复劳动。**

## 五、最后：对"完美"的诚实预期

- **能保证的**：色值、尺寸、圆角、字阶、间距 100% 一致（走同一份令牌，无歧义）
- **能做到但要逐个测**：交互态观感一致（本次 Button 做到了 54 项组合全绿）
- **做不到的**：API 写法一致（`className="btn-text"` vs `text`）、
  部分 JS 行为（loading 宽度）、以及**未知的、只有跑起来才会暴露的差异**

**建议的验收口径**：不承诺"零差异"，承诺"**所有差异都被记录在 DIFF.md 里、且每条都有明确处置**"。
这比一个做不到的"完美"承诺更可靠，也更符合你「有差异要让我知道」的要求。
