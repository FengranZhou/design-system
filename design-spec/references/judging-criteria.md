# 设计规范评判标准

> **这是什么**：一套用来给「接入了本设计系统的项目 / 页面」打分的检查清单。
> 每一条的判据都来自本仓库已定义清楚的规则（令牌、组件源头、模式文档），**本文件不新增任何规则**。
>
> **两个用途**：① 设计师对照条目人工检查；② 脚本扫接入方代码自动评分。
>
> **本文讲「规则怎么定义」**（标记语法、分级口径、条目从哪来）。
> **要知道「脚本怎么用」看 [`scripts/README.md`](../../scripts/README.md)**——
> 三种使用场景、怎么读报告、误报如何豁免。

---

## 一、条目从哪来（核心机制：投影，不是副本）

评判条目**不是另写一份清单**，而是从各规范文档正文里**提取**出来的：

```
references/*.md 里的规则行
        │  行末打 @rule 标记
        ▼
scripts/extract-rules.mjs   ← 提取
        │
        ▼
references/rules.generated.json   ← 唯一消费入口
        │
        ├──→ demo「评判标准」页（人工对照 + 打分）
        └──→ 接入方代码评分（规划中）
```

**为什么这么设计**：如果条目是手抄的副本，规范一改它就过期，必然长出「规范说 A、清单说 B」的裂缝——这正是 `audit-spec.mjs` 一直在防的东西。做成投影后，**改规范 = 改条目**，天然同步。

**由此得出一条纪律**：要改某条评判标准，去改它 `source` 指向的规范原文，**不要改 `rules.generated.json`**（那是生成物，会被覆盖）。

## 二、标记语法（新增规则时怎么让它进评判标准）

在规则行末尾加一段 HTML 注释（md 渲染时不可见，不影响文档阅读）：

```markdown
- ❌ 硬编码颜色值（如 `color: #23B283`） <!-- @rule id=color-no-hardcode level=MUST cat=设计令牌 detect=regex dtitle=颜色应取自色板，不应出现色板外的杂色 -->
```

> 提取器会**跳过 ``` 围栏代码块内的标记**，所以文档里写示例不会被误当成真条目。

| 字段 | 必填 | 取值 | 说明 |
|---|---|---|---|
| `id` | ✅ | kebab-case，全局唯一 | 稳定不变，用于跨版本追踪同一条目。**改措辞不要改 id** |
| `level` | ✅ | `MUST` / `SHOULD` / `MAY` | 决定权重与是否卡红线 |
| `cat` | ✅ | 见下方类别表 | 决定条目在评判页里的归组 |
| `detect` | ✅ | `regex` / `ast` / `manual` | 检测方式；`manual` = 只能人工判定 |
| `view` | ⬜ | `design`（默认） / `impl` | 条目视角，见下方说明 |
| `weight` | ⬜ | 正数 | 覆盖 `level` 的默认权重 |
| `dtitle` | ⬜ | 文本 | **设计措辞**：同一条规则给设计师看的说法（讲现象、不讲 API）。写了它，该条目在两个视角下各以对应说法出现 |
| `title` | ⬜ | 文本 | 覆盖条目标题（默认取规则行正文，正文太长或含大量嵌套格式时建议显式写） |

> `dtitle` 与 `title` 都是**长值字段**（值为整句中文、含空格），必须写在标记末尾，且 `dtitle` 在 `title` 之前。

**类别表**（按**本仓库自身的规范体系**划分——令牌 / 组件 / 模式 / 文案四层 + 单一数据源根基，每类都能直接对应到一份规范文档）：

| 类别 | 管什么 | 判据主要在 |
|---|---|---|
| **单一数据源** | 禁 scoped 私货、三层接入顺序、禁拷贝式接入 —— 违反即全盘脱钩 | 最高铁律（`CLAUDE.md`）+ 本文件 §五 |
| **设计令牌** | 颜色 / 字号 / 间距 / 圆角 / 阴影 / 动效一律走令牌，禁裸值 | `foundations.md` |
| **组件选用** | 该用哪个组件：勿用清单、禁手撸等价物、业务组件优先 | `component-interaction.md` 两份清单 |
| **组件用法** | 选对了怎么用：必传 prop、约定 class、禁覆盖外观 | `component-interaction.md` 各组件段 |
| **布局与栅格** | 栅格档位、1200 硬下限、分隔手法 | `efficiency-guide.md` |
| **设计模式** | 表单 / 表格 / 工具栏 / 弹窗 / 搜索的组织方式 | `references/patterns/` |
| **状态设计** | 加载 / 空态 / 错误态 / 禁用态 | `efficiency-guide.md` + 组件段 |
| **文案规范** | 时间格式、标题写法等展示口径 | `references/copywriting/` |
| **视觉呈现** | 主按钮位置、装饰克制、层级对比 —— 人工判定为主 | `foundations.md` + `display-guide.md` |

> 顺序即页面展示顺序，也大致是「违反后果由重到轻」。
> 类别是**封闭集合**，写了表外的值提取器会报错。确需新增类别时改 `scripts/extract-rules.mjs` 的 `CATEGORIES`。

### 视角与措辞：同一条规则，两种说法

**关键认识：同一条规则，设计师与研发看到的是不同的东西。**

以「`el-button` 的 type 仅允许 `default/primary/danger`」为例——研发看的是 prop 取值；设计师看到的是「页面上冒出一个橙色按钮」，他判断得了现象、却说不出 API 名。若只用技术措辞，这条对设计师等于不存在；若只用视觉措辞，研发又无从落地。

所以**不要二选一地把条目丢给某一边**，而是写 `dtitle=` 给出设计措辞，该条目便在两个视角下各以对应说法出现：

| | 技术措辞（`title`） | 设计措辞（`dtitle`） |
|---|---|---|
| 按钮类型 | `el-button` 的 type 仅允许 default/primary/danger | 按钮只有默认/主要/危险三种，不应出现其他颜色的按钮 |
| 纯图标按钮 | 禁用 `circle` 属性做纯图标按钮 | 不应出现圆形的纯图标按钮 |
| 弹窗 | 弹窗统一用 `el-dialog`，不引入 ElMessageBox | 所有弹窗观感一致，不应有长得不一样的系统弹窗 |
| 空状态 | `el-empty` 必须同时传 `:image` 与档位 class | 空状态应使用设计系统插画，不是默认的灰色纸盒图 |

**三种归属**：

| 归属 | 怎么写 | 什么情况 |
|---|---|---|
| **两个视角都出现** | 写 `dtitle=` | 多数条目。规则同一条，只是观察角度不同 |
| **只在设计视角** | 不写 `dtitle`，`view` 用默认 | 纯视觉判断，本来就没有技术措辞（主按钮贴边、装饰克制、弹窗标题写法） |
| **只在实现视角** | 写 `view=impl`，不写 `dtitle` | **页面上完全看不出来**：scoped 私货、样式三层引入顺序、拷贝式接入、下游 `@` 引入 |

> **判据**：先问「设计师盯着页面能发现这里不对吗」——
> 能，就要有 `dtitle`（哪怕规则本身是技术措辞）；完全看不出、只有读源码才知道，才写 `view=impl`。
>
> ⚠️ **不要偷懒把技术措辞直接丢进设计视角**——「禁用 circle 属性」对不动代码的设计师是无效条目，他既判断不了、也不知道该看什么。

打完标记跑一次：

```bash
node scripts/extract-rules.mjs
```

## 三、分级与评分口径（两套并行，同一份条目）

### 分级（自动化门禁用）

| 分级 | 含义 | 默认权重 | 违反后果 |
|---|---|---|---|
| **MUST** | 违反即不合规。名单越界 / 功能断裂 / 脱离单一数据源 | 3 | **卡红线**，必须修 |
| **SHOULD** | 偏离标准做法，但功能正常 | 2 | 需说明理由 |
| **MAY** | 优化建议 | 1 | 记录不阻断 |

> 分级口径与 `component-interaction.md` 的「反模式优先级」（BLOCKING / STRONG / SOFT）同源：BLOCKING → MUST，STRONG → SHOULD，SOFT → MAY。

### 百分制（对外汇报用）

```
得分 = Σ(通过条目的权重) / Σ(适用条目的权重) × 100
```

- **85 分为合格**
- **「不涉及」的条目不计入分母** —— 页面里没有表单，表单类条目就不参与计算，避免用不到的条目稀释分数
- 扣分项需**举证说明**（写清违反位置与具体表现），不能只打个叉

## 四、检测方式说明

| detect | 含义 | 举例 |
|---|---|---|
| `regex` | 正则扫源码即可判定 | 「禁用 `el-row`」→ 搜 `<el-row`；「必传 `show-after`」→ 找出所有 `el-tooltip` 检查是否带该 prop |
| `ast` | 需解析语法树才能准确判定 | 「同一层级最多一个 Primary 按钮」需理解组件嵌套结构 |
| `manual` | 只能人工判定 | 「主按钮贴边」「弹窗标题写清操作对象」——涉及语义与视觉判断 |

> **`manual` 不等于不重要**：这类条目往往是设计质量的关键（主按钮位置、标题文案），只是机器判不了。设计师人工对照时**重点看这些**。

## 五、单一数据源类目（本节自身承载条目）

以下条目的判据在根 `CLAUDE.md` 与 `design-spec/CLAUDE.md` 的最高铁律里，是整套设计系统能成立的根基。因提取器只扫 `references/`，在此承载：

- **组件外观只能定义在源头 `el-theme/components/`，使用方不得在 scoped（含 `:deep()`）里重新定义或覆盖组件外观**（字号 / 字重 / 颜色 / 边框 / 圆角 / 选中态 / 装饰 / 溢出行为等外观类属性）。违反即「局部私货」——该处脱离源头、不再随源头同步，是最典型的翻车。 <!-- @rule id=ssot-no-scoped-override level=MUST cat=单一数据源 view=impl detect=regex title=禁在使用方 scoped/:deep() 里覆盖组件外观（局部私货，脱离源头不再同步） -->

- **必须引入三层且顺序固定**：① `element-plus/dist/index.css` → ② `design-token/index.scss` → ③ `el-theme/index.scss`。顺序错了覆盖会失效。 <!-- @rule id=integration-three-layers level=MUST cat=单一数据源 view=impl detect=regex title=必须按固定顺序引入样式三层（EP 基础 → 令牌 → 组件覆盖层） -->

- **严禁「拷贝式」接入**：不得把 `design-token/` 或 `el-theme/` 的 scss 拷贝进引用方仓库——拷贝即脱离源头，源头更新它不动。只能通过相对路径 / npm 包 / submodule / monorepo 共享指向同一份源头。 <!-- @rule id=integration-no-copy level=MUST cat=单一数据源 view=impl detect=manual title=严禁拷贝式接入（拷贝 scss 进自己仓库＝脱离源头） -->

- **下游项目根 `CLAUDE.md` 须用 `@` 引入本设计系统的 `design-spec/CLAUDE.md`**，否则下游 CC 只拿到样式、拿不到设计模式与组件用法规则。 <!-- @rule id=integration-claude-at-import level=SHOULD cat=单一数据源 view=impl detect=regex title=下游根 CLAUDE.md 须 @ 引入 design-spec/CLAUDE.md（否则下游 CC 读不到规则） -->

- **业务组件层同样受铁律约束**：用到基础组件只引用不覆盖、token 复用不够时先确认、只装扮自己的骨架不碰基础组件外观。 <!-- @rule id=biz-component-no-override level=MUST cat=单一数据源 view=impl detect=manual title=业务组件只装扮自己骨架，不覆盖所用基础组件的外观 -->

## 六、维护纪律

1. **新增强制规则时一并打 `@rule` 标记** —— 漏打由 `audit-spec.mjs` 的 **C8 检查硬拦截**（报错退出，非提示）。

   > **确实不该成条目时，用 `@rule-skip` 显式豁免**，两种正当理由：
   > ```markdown
   > - **某条规则** <!-- @rule-skip dup 已由 xxx-rule-id 覆盖 -->
   > - **某条规则** <!-- @rule-skip n/a 能力描述表的一行，非可判定规则 -->
   > ```
   > `dup` = 同一规则在别处已有条目，此处只是另一处表述（如反例行、速查表复述）；
   > `n/a` = 措辞像规则但不可判定（子风格能力描述、"非首选但不禁止"这类无强制力的表述）。
   > **理由必须写清**——豁免是给规则开的口子，写明白才能在日后复核时判断它是否仍然成立。
2. **改规则措辞不要改 `id`** —— id 是跨版本追踪同一条目的锚点。
3. **改完跑一次提取** —— `node scripts/extract-rules.mjs`，CI 用 `--check` 校验生成物是否与标记一致。
4. **不要手改 `rules.generated.json`** —— 生成物，会被覆盖。

> **能力边界（继承自 `audit-spec.mjs` 的自陈）**：本清单只覆盖「已被标记的规则」。**跑通 ≠ 页面设计得好**，只是没有清单内这些已知问题。信息密度、视觉层级、文案得体这些仍须人工审。
