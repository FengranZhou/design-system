# 业务组件层公约 —— Business Component Layer

> **本文件是「业务组件层」的正式规矩与调用方式，供任何在本目录下工作的人 / CC 会话自动加载。**
> 新开 CC 窗口进入本目录即受本公约约束，无需用户重复交代。
> 本公约在「基础组件层最高铁律」（见 `design-spec/CLAUDE.md`）之下、之内——业务组件层是它的延伸，不是例外。

---

## 一、这一层是什么

本设计系统分两层：

| 层 | 位置 | 本质 | 有无自己的 DOM |
|---|---|---|---|
| **基础组件层** | `el-theme/components/*.scss` | 原生 Element Plus + 一层 SCSS 皮肤覆盖（换外观，行为归 EP） | 无，借 EP 的 DOM |
| **业务组件层**（本层） | `design-spec/components/<Name>/*.vue` | **多个基础组件 + 布局 + 业务逻辑组合成的「成品」** | **有自己的 Vue 模板/DOM** |

一句话：**基础组件是「给 EP 换皮肤」，业务组件是「用基础组件搭出的成品」。** 业务组件面向各业务方直接调用（如 AI 面板、审批卡片、课程卡等）。

**源头唯一**：每个业务组件只此一份定义，放在本目录，各方 `import` 引用同一份——改源头处处同步。这与基础组件层的「单一数据源」是同一个道理。

---

## 二、⛔ 三条铁律（每个业务组件都必须遵守）

### 铁律 1 —— 用到基础组件：直接引用，绝不覆盖

业务组件内部要用按钮、输入框、标签等，一律用**已有的基础组件**（`el-button` / `el-input` / `el-tag` …），原样引用，**不手撸等价物、不覆盖其外观**。

- ⛔ **红线**：业务组件的 `<style scoped>` 里**严禁**出现 `:deep(.el-button){…}` / `:deep(.el-input__inner){…}` 这类**修改基础组件外观**的规则（字号 / 字重 / 颜色 / 边框 / 圆角 / 选中禁用态 / 装饰 / 溢出行为）。
- ✅ **要改基础组件外观 → 永远回 `el-theme/components/<组件>.scss` 源头改**，改完所有业务组件与项目一起同步。
- ⚠ 需要的基础组件**不存在**时，先向用户确认新增，不临时拼装。

### 铁律 2 —— token 尽量复用，不符合先确认

所有样式值（颜色 / 间距 / 圆角 / 字体 / 阴影 / 动效）优先引用 `var(--iflyv-*)` 设计令牌（定义见 `design-spec/design-token/`）。

- ⛔ **禁止裸值**：硬编码 hex 色、`px` 魔法间距、字面字号 / 行高 / 字重。
- ⚠ 令牌**确实覆盖不了**某个业务特有的值（如 AI 面板要的特殊品牌渐变）时，**停下来向用户确认**「应新增哪个令牌」，由用户决定新增全局令牌，而不是就地硬编码。

### 铁律 3 —— 自由发挥合法，但只限「装扮自己的盒子」

业务组件**有自己的 DOM 骨架**，排布自己骨架的 scoped 样式是**合法且鼓励**的——这正是它区别于「纯皮肤覆盖层」的地方，也是业务组件该有的灵活度。

**判据（业务组件层最容易翻车的一条线，务必分清）：**

> **「这条样式是在装扮我自己的盒子，还是在改别人（基础组件）的盒子？」**
> **装扮自己 → 放行；改别人 → 回源头。**

| 情形 | 判定 | 例子 |
|---|---|---|
| 排**自己的** DOM 骨架 | ✅ 合法自由发挥 | 面板标题栏高度、消息流间距、自己的圆角 / 背景 / 渐变、自定义布局 grid/flex |
| 改**基础组件**的外观 | ⛔ 违规私货，回源头 | `:deep(.el-button){ border-radius:… }`、`:deep(.el-input__inner){ color:… }` |
| 用**裸值**代替可用令牌 | ⛔ 违规，先问再定 | `padding: 13px`（应 `var(--iflyv-spacing-3)`） |
| 令牌**确实没有**的新值 | ⚠ 暂停确认 | 业务特有渐变，令牌里没有 → 问用户是否新增令牌 |

即：业务组件的 scoped **只能放「自己骨架的排版 / 装饰」**，**不得触碰基础组件本身的外观规则**。

## 三、目录结构（每个业务组件的标准形态）

```
design-spec/components/
├── CLAUDE.md                      ← 本公约
├── index.ts                       ← 业务组件层【统一导出入口】，各方只 import 这一个
└── <BizComponent>/                ← 一个业务组件一个目录，PascalCase 命名
    ├── <BizComponent>.vue          ← 模板(引基础组件) + 逻辑 + scoped(自己骨架，走令牌)
    ├── index.ts                    ← 该组件的导出
    └── types.ts                    ← props / emits 类型（可选，复杂组件才需要）
```

约定：
- 组件目录名、组件名、`.vue` 文件名一律 **PascalCase**（如 `AiPanel/AiPanel.vue`）。
- 业务组件的骨架样式写在**自己的 `.vue` scoped 里**，**不塞进 `el-theme/`**（那层只放基础组件皮肤）。
- 新增组件后，在本层 `index.ts` 统一 re-export，保证各方只需引一个入口。

## 四、✅ 正规调用方式（决定「同步」是否成立的前提）

业务组件层延续基础组件层的接入范式：**相对路径引用同一份源头，不拷贝、不魔改**。

### 4.1 前提：先按顺序接入基础三层（样式底座）

业务组件依赖基础组件的皮肤，使用方必须**先**接好基础三层（顺序固定，见 `demo/src/main.ts` 范本）：

```ts
// main.ts —— 样式加载顺序：EP 基础 → 设计令牌 → 主题覆盖
import 'element-plus/dist/index.css'                    // ① EP 基础
import '<path>/design-spec/design-token/index.scss'     // ② 设计令牌
import '<path>/design-spec/el-theme/index.scss'         // ③ 组件覆盖层
```

> 顺序错了覆盖会失效。`<path>` 是指向**同一份源头**的相对路径 / npm 包 / submodule / monorepo 共享——**严禁拷贝源头进自己仓库**（拷贝 = 脱钩，源头更新它不动）。

### 4.2 引用业务组件（本层）

接好三层后，从业务组件层的**统一入口** import：

```ts
// 本仓库 demo 用相对路径指向同一份源头
import { AiPanel } from '../../design-spec/components'
```

```vue
<template>
  <AiPanel :title="..." @submit="..." />
</template>

<script setup lang="ts">
import { AiPanel } from '../../design-spec/components'
</script>
```

> 将来给**外部独立项目**用时，才需把 `design-spec` 打成 npm 包（配 `package.json` 的 `exports` 指向 `components/index.ts` + 必要构建），届时 import 改为包名即可，**规矩不变**。当前阶段走相对路径，零构建改动。

### 4.3 接入方同样受铁律约束

- 使用方**不在自己的 scoped 里覆盖基础组件外观**（同铁律 1 红线）。
- 使用方**不拷贝**源头、**不逐个引子文件**（只引统一入口）。
- 由此得出：**对正规接入（引全三层 + 引业务组件统一入口 + 不拷贝 + 不写私货）的项目，`demo/` 的效果就是它们引用后的真实效果，分毫不差。**

## 五、落地前自检（每加 / 改一个业务组件，逐条核对）

1. 用到的基础组件是否**直接引用、无 `:deep` 覆盖其外观**？（命中→回 `el-theme` 源头）
2. 样式值是否**全走令牌**、无裸值？令牌不够时是否**已暂停向用户确认新增**？
3. scoped 样式是否**只装扮自己的骨架**、没碰基础组件外观？
4. 是否在本层 `index.ts` 统一导出、使用方能从单一入口引用？
5. 命中「找不到基础组件 / 找不到令牌 / 想覆盖基础组件外观」时，是否**已暂停并向用户说明**，由用户定夺？
